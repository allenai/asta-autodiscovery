Surprise-Reward RL — how the pieces fit

RL training · Bayesian-surprise reward

One policy on GPUs. One reward server off to the side.
Here's the round trip.

The model being trained proposes a scientific hypothesis. To score it, something has to actually run an experiment and measure how much the result changes what we believe. That scoring is too heavy — and too incompatible — to live inside the trainer, so it runs as a separate HTTP service the trainer calls once per generated sample.

Trainer — slime · Megatron · SGLang · 8×GPU · Python 3.13 Reward server — autodiscovery · CPU · Python 3.10

02 — inside "Score": belief, surprise, verdict

The reward is how far one hypothesis moves a belief

The belief is a single number in [0, 1]: how likely the hypothesis is true, read off a five-category distribution. It's elicited twice — a prior (before running the experiment) and a posterior (after seeing the result). The gap between them is the surprise.

03 — concurrency

One server, 48 slots — not 48 servers

--concurrency 48 is one reward-server process running up to 48 experiments at once — an internal worker pool, not 48 separate servers. A step produces batch 8 × samples 8 = 64 hypotheses, so 64 requests arrive; 48 run in parallel and the other 16 wait in a queue until a slot frees. What "spins up" per experiment is an isolated sandbox venv (to run the generated code), never another server.

1 reward server · pool of 48 slots · 64 requests/step■ running(48)   □ queued(16)
each cell = one in-flight experiment (its own sandbox venv); at most 48 at a time

the arithmetic

64 hypotheses / step
× ~3 min per experiment
──────────────
serial: ~3 hours / step
48-wide: ~4 min / step

The GPUs would sit idle for that whole window — so the reward server, not the trainer, owns this parallelism.

04 — serving a task on a server

How the server knows which dataset to run against

"A task" here is a dataset — affairs, nls_raw, and so on. At startup the server loads a registry mapping each dataset id to its data + metadata. Every reward request carries a dataset_id, and a router sends it to the right dataset's experiment runner. That's what "serving a task on a server" means: the task is registered once, then addressed by name on each call.

dataset_id: affairs→ router →affairs data + metadata → run experiment
dataset_id: nls_raw→ router →nls_raw data + metadata → run experiment
dataset_id: boxes→ router →boxes data + metadata → run experiment
request_id: 7-a3f1…→ dedupe →seen before? return cached — never re-run a paid, multi-min experiment

05 — why a separate server at all

Why the reward doesn't just live inside the trainer

The natural question: why not import the scoring code into slime and call it directly? Three reasons it has to be its own process, reached over HTTP.

01 · isolation

Incompatible Pythons

slime needs Python 3.13; autodiscovery needs 3.10. They cannot share one interpreter. An HTTP boundary lets each keep its own env and dependency tree.

02 · contract

No shared imports

slime never imports autodiscovery — it only speaks a tiny JSON contract: POST /reward in, {reward} out. Either side can change internally as long as the contract holds.

03 · workload

Different resource shape

Training is GPU-bound and synchronous; scoring is CPU/API-bound and massively parallel (48 experiments, each shelling out to models + a sandbox). Kept apart, neither starves the other.

The one-liner: the policy proposes hypotheses on the GPUs; a sidecar HTTP server runs a real experiment per hypothesis and returns Bayesian surprise as the reward; concurrency lives in that server because experiments are slow and many; the split exists because trainer and scorer can't share a Python — or a resource profile.
