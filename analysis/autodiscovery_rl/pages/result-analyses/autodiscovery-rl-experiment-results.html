  • Always-0 and always-1 are provably inert: constant rewards → zero group std → zero GRPO advantage → grad norm exactly 0, KL 0, policy frozen. The frozen runs even reproduce identical seeded generations across experiments — the no-update path is truly a no-op.
  • Coin flip is the only run where gradients flow: KL climbs monotonically to 0.116, entropy falls 0.70 → 0.61, responses shorten. Pure noise-drift, exactly what random reward should do. This confirms the reward → advantage → update path works end-to-end.
  • Codex rewards were never actually exercised. v1: every sample failed with codex CLI 401 Unauthorized (OPENAI_API_KEY doesn't authenticate its Responses-API calls). v2: codex login --with-api-key fixed auth, but /usr/local/bin/codex-code-mode-host was missing (the standalone musl tarball doesn't ship it), so every experiment returned "Inconclusive" → reward 0. Both collapsed to the always-0 case. A v3 needs the code-mode host installed.

Reading: within the fixed commit, related vs open-ended shows no detectable difference — ~70% surprise and ~0% exec failures either way. All four binrw[-trunc01]-fb-g4/g16 runs were canceled at ~step 8 with degenerate rollouts (reward 0, truncation 75–100%), so the triplet mechanism has produced no usable numbers yet.

Reading: the ≥0.2 threshold is crossed so rarely on archaeology that groups are nearly all-zero — GRPO's zero_std guard fires and advantages vanish, so there is essentially no learning signal. Reward does not trend up (the final-step 0.25 in binrw-g4 is a single 1/4 group, i.e. noise). Continuous baselines start higher (0.17–0.21) and decline. Binary rewards starved the signal rather than fixing the trend.

Does a response penalty mitigate length growth? Binary reward + penalty

works at g16

Jobs binrw-trunc01-g4/g16 (Aug 19; adds FAILURE_REWARD=-0.1 for truncated/failed rollouts).

RunResp len step0 → step9Truncated frac (max)W&B
binrw-g16 (no penalty)8070 → 161220 → 0.875 (0.94)dwihdkkr

binrw-g4 (no penalty)9958 → 79630 throughoutxzr7sx89
binrw-trunc01-g48040 → 79000 throughoutc38bnfo2

Reading: at g16 the penalty clearly prevented the blow-up — flat ~8.5k → 9.8k tokens with 0% truncation, vs ~2× growth and 88–94% truncation without it (continuous g16-v3 hit the 16,384 cap with 100% truncation). At g4 neither run ever truncated, so there was no pathology to correct. Caveat: with rewards near-uniformly zero, the penalty may work partly by removing the only nonzero-advantage updates rather than actively teaching brevity — but empirically it held length flat.

Cross-cutting observations & follow-ups

  • Unreconciled discrepancy: the slime reward path fails 90% of executions on policy-written hypotheses, while baseline-engine runs at the same commit fail ~0% on engine-generated ones. Differences to investigate: max_rounds=10 + single-revision selector in the reward server, hypothesis quality/token hygiene from the policy (trailing <|im_end|>), and column grounding.
  • Token usage is only recorded going forward: everything above ran at fbafd54; the metrics commit 655e6ff (per-experiment [metrics] line + run_metrics.json, verified by smoke test: 2 experiments, 35 calls, 1.30M tokens) now captures it for both paths.
  • Codex v3: install the codex-code-mode-host binary (npm layout, not the musl tarball) before rerunning — codex reward remains completely untested.
  • Rerun the fb (triplet) runs with the truncation penalty — the penalty demonstrably prevents the g16 truncation death-spiral that killed them.
  • Binary threshold is too sparse on archaeology (~0–12% of samples cross 0.2). Options: lower the threshold, use continuous |normalized surprisal|, or pick a higher-surprise task (per n500_failure_rates: affairs 73.6% success / 121 surprising, crofoot, fish).
  • Pull related-n500 final numbers when it finishes (was still running Aug 21) for the definitive related-vs-open-ended comparison.
