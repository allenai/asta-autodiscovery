Why experiments spiral into failed-code retry loops

Each training step waits on 64 parallel experiments; the slowest — the straggler — sets the wall-clock. Stragglers are almost always experiments stuck in long programmer → execute → analyst rounds, each round tripped by a self-inflicted code failure. This is the measured distribution of what actually fails, mined from the raw reward-server logs.

Root causes, ranked by leverage

Six patterns account for nearly all the churn. Each failure fires analyst → reviser → re-programmer → re-execute; imprecise feedback means fixing error A often just surfaces error B, so a single experiment accretes rounds.

01

Stale library-API knowledge vs. the sandbox's newer versions

The model learned older pandas / matplotlib / statsmodels signatures; the sandbox runs newer ones. Correct-looking code fails on renamed kwargs and removed methods, and the analyst rarely knows the version-specific fix — so it thrashes. The single most fixable bucket.

boxplot() got an unexpected keyword 'labels'536× 'GLMResults'/'LogitResults' has no attribute 'get_robustcov_results'~440× Multi-dimensional indexing no longer supported89×
Fix

Pin or announce library versions in the programmer's system prompt (or pin the sandbox to the versions the model knows). Kills this bucket outright.

02

pandas ↔ numpy type confusion

The model loses track of whether a variable is a DataFrame/Series or a bare ndarray and calls the wrong API — .loc/.index on an array, or feeds object-dtype frames into numeric ops.

'numpy.ndarray' object has no attribute 'index' / 'loc' / 'get'~1150× Pandas data cast to numpy dtype of object545× int() argument must be … not 'Series'; only N-dim arrays → scalars~600×
Fix

Smaller, incremental code blocks with intermediate type/shape asserts, so a mistaken type surfaces in one line instead of corrupting a 22 KB block.

03

Guessing the data schema instead of inspecting it

Analysis code written before checking what's in the file — referencing columns and category levels that don't exist. Recurs across every experiment on a dataset, so the cost compounds.

KeyError: 'CountryGroup' / 'mean' / 't'~2950× PatsyError: specified level 'Homo' not found55×
Fix

A schema preflight the planner enforces — print df.columns, dtypes, and value_counts() before any analysis. Also removes much of bucket 02.

04

Statistical-modeling misuse

statsmodels formulas and result objects used incorrectly: formulas referencing missing variables/levels, singular design matrices from collinear predictors, and NaNs fed into regressions.

PatsyError: model is missing required outcome variables270× LinAlgError (singular matrix / collinearity)180× MissingDataError (NaNs into regression)37×
Fix

A statsmodels crib in the prompt (dropna before fit, VIF/collinearity check, correct result-object accessors) — partially overlaps the version-pin fix.

05

Missing imports & assumed-persistent state

References to things never imported, or variables a prior (failed) block never created — the code assumes state carries across execution turns when it may not.

NameError: 'sm' / 'stats' / 'variance_inflation_factor' not defined~1160× 'sm' not defined, did you mean 'smf'?24×
Fix

Require explicit imports every block and no cross-block state assumptions — each executed block self-contained.

06

Malformed / truncated code emission

The LLM emits syntactically broken or truncated code — strongly correlated with big monolithic blocks (p90 ≈ 22 KB). One bad line invalidates the whole block and forces a full rewrite.

SyntaxError1558× IndentationError262× _IncompleteInputError (truncated block)66×
Fix

Smaller blocks again — shrinks the surface for truncation and makes any single failure cheap to repair.

Straggler blowups — from the rollout records

The six buckets above are code-execution failures mined from stdout. To find what makes a single experiment run long — the straggler that gates the whole step — I pulled the per-rollout record dumps (rollout_records_<fmt>.jsonl: reward, surprise diagnostics, and the full trace per hypothesis) from every run. The tail collapses to one cause.

Reward is gated by a reviewer/executor check (slime_reward.py:298). Every experiment runs programmer→executor→analyst→reviewer; if the reviewer rejects it — with only ≤1 revision allowed (line 102) — it returns reward 0 as "experiment failed executor/reviewer checks" and never reaches belief elicitation. Stragglers are these failed experiments: they burn the full revise-then-reject cycle plus verbose rejected output before returning nothing.

why

One rate drives both the slow steps and the flat reward

Stragglers ≈ failures. For luna, failed traces (27.2k chars) run markedly longer than passing ones (19.6k) — passes finish fast, failures drag through the revise cycle and balloon (some to the 100k trace cap). The longest traces are ~all reward-0 (46/46 in luna 4×4). The flat reward is the same event: a 60% auto-zero rate collapses the batch mean and manufactures the zero-std groups.

Execution-side confound, now proven from the records (no offline re-score needed): luna and gpt-5.6 fail the gate at ~60%, mini at 28%. Since the reviewer is the execution model, this may be luna/gpt-5.6 acting as stricter self-reviewers rather than doing worse science — note even the stronger gpt-5.6 sits at 59%, so it is not a "weak model" effect.

Lever

Decouple or calibrate the reviewer (a fixed reviewer model across runs), and/or allow >1 revision (slime_reward.py:102). Both attack step-time and reward signal at once — the failed-experiment tail is where the wasted wall-clock and the dead gradient both live.

Inside the reviewer gate — the 30% that returns nothing

The gate rejects ~30% of mini's experiments (≈60% for luna / gpt-5.6). To find why, I pulled all 189 rejected records from a mini A/B (2026-08-04) and read the verdicts against the reviewer's own instructions. Almost none are code crashes — they are the reviewer applying a maximally strict rule.

Root cause is the reviewer's prompt. The experiment_reviewer is told: "If you find issues or inconsistencies in any part of the experiment pipeline, return success = false." — an all-or-nothing gate, with only ≤1 revision allowed (slime_reward.py:102). A perfectionist LLM reviewer can always find one more thing to want, so success is capped near ~70% by construction.
M1

Perfectionism — "please re-run / add X"

The dominant mode: the verdict ends by requesting more — another robustness check, a saved output file, one more diagnostic — that the ≤1-revision budget can never deliver. Incompleteness is treated as failure.

verdict asks for a re-run / missing artifact~90%wants more diagnostics / robustness~97%

"…the experiment cannot be considered fully successful [until] these remaining analyses are completed and the artifacts resolved." — fish

M2

Reward entangled with hypothesis truth

Experiments failed because the hypothesis was refuted / non-significant. But this is a Bayesian-surprise reward — a rigorously-run experiment that refutes its hypothesis is exactly what should score high. Gating reward on success, and success on "hypothesis supported," fights the reward objective. The single most reward-relevant mode.

fails because result was refuted / not significant~31%

"…the interaction fails to be cluster-significant … the experiment's main hypothesis is not conclusively supported." — teachingratings

M3

Hypothesis ↔ data mismatch

The policy proposes hypotheses needing data the dataset doesn't contain — a country mapping, a label subset — so the experiment can't fully test them and the reviewer rejects rather than accepting the testable subset. Partly upstream (constrain generation to real columns), partly reviewer strictness.

references columns / mappings not in the dataset~75%

"Because the missing mapping prevents the Namibia vs Japan comparison … therefore success = false." — boxes

M4

Worked-but-failed on a found issue

The primary result was obtained and significant, but a minor or already-fixed issue elsewhere in the pipeline trips the "any issue → false" rule. A pure false-negative. Subsumed by M1's strictness.

primary result obtained, still marked false~29%

"…a statistically significant negative association [was obtained]. However, per the developer instruction … if any issues … you must return success = false." — immigration_offshoring

Prevalences overlap (a verdict can hit several) — read as theme frequencies, not a partition. n = 189 reviewer-gate rejections, mini · fmt1 · 4×4.

Effect on step time — a reward lever, not a speed lever (for mini)

Does the gate slow steps? Only if rejected experiments run longer — i.e. if they are the stragglers. For the mini executor we're standardizing on, they are not.

so

For mini, fixing the gate recovers reward, not wall-clock

Mini's rejected experiments take the same time as its passing ones (1.02×), and are under-represented among the longest traces — so the ~31% of compute spent on eventually-rejected experiments is proportional, not a straggler concentration. Softening the gate would recover the reward those experiments should have earned (especially M2's refuted-but-valid ~31%), but would not speed up steps — and allowing >1 revision would slightly increase step time. Luna is the mirror image: its failures run 1.39× longer, so there the gate is simultaneously a reward and a step-time drag ("Stragglers ≈ failures" above).

Takeaway

Reviewer-gate fix = a reward lever for mini — recovers the 30% auto-zero and, via M2, un-entangles reward from hypothesis truth. Step time is a separate lever (the code-failure retry rounds, buckets 01–06). Don't expect the gate fix to speed up mini steps.

Two data sources, two granularities: the six buckets are raw exception occurrences in reward-server stdout (relative distribution, not per-experiment counts); the straggler table is exact per-rollout records (rollout_records_<fmt>.jsonl) pulled from each run's Beaker result dataset. Code-exec failures (buckets) are one way an experiment fails the reviewer gate; the gate itself (and its ≤1-revision budget) is the straggler mechanism. Fixing the reviewer/revision policy and the top code-failure buckets both shrink the failed-experiment tail — which is simultaneously the slow-step tail and the zero-reward tail.
