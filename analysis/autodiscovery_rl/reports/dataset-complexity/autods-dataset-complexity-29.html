Interpretation for g256

  • Keep g256 for reward sparsity/diversity, not because tables are large. Sampling cost is fixed by group size; raw-data complexity mainly changes reward-evaluation latency and failure risk.
  • Do not treat all 29 tasks as equivalent. The top cluster combines very wide schemas, multiple files, large n, or heavy missingness; the bottom cluster consists mostly of compact single tables.
  • Separate power risk from operational complexity. Tiny or p≈n datasets can be statistically fragile even when cheap to load. That can make binary surprise noisier.

Method and limitations

  • Raw CSV/DTA tables were read directly. Tab-delimited files with a .csv suffix were detected from their header. The phylogenetic tree is counted as an auxiliary source, not forced into a table.
  • The relative complexity index is intentionally transparent, but its weights are judgment calls. Use the component columns and flags for scheduling decisions rather than treating a one-point score difference as meaningful.
  • Missingness is cell-weighted. Type mix uses parsed storage types; numeric-coded categories are separately counted in the machine-readable export but do not change the headline index.
  • nls-raw and nls-bmi-raw reference the same 12,686 × 61 raw NLS table. They remain separate because they are separate benchmark tasks and prompt histories.
  • Prompt measurements reproduce Slime’s filter path: apply the Qwen3.5 chat template, tokenize the rendered string with add_special_tokens=False, then compare with --rollout-max-prompt-len.
Companion CSV and JSON contain the exact metrics and per-file profiles.
